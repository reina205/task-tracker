# Reflection — Mid-Course Project

For this project, I used Claude to help implement both features on top of my existing Task Tracker: due dates with an overdue filter, and tags/labels. I worked through the ask, inspect, run, test, refine loop for each one, rather than accepting generated code without checking it.

One place AI genuinely helped was speed and thoroughness on the backend logic. When I asked for the due-date model changes, Claude proposed computing "overdue" as a read-time property rather than a stored one, so the value always reflects the current date instead of going stale. It also generated a fairly complete set of edge-case tests on the first pass, invalid formats, the Done-task exception, filtering with no matches, that lined up closely with the "good tests to include" column in the assignment brief.

The clearest case where AI actually slowed the work down, rather than my own environment issues, was a validation bug that made it all the way into my original submission. When Claude wrote the `TaskUpdate` model, the `title` field validator had a line that said "if the value is None, just return it unchanged." That looked reasonable when I read it, since the field is optional and I assumed None meant "the field wasn't sent." But that was wrong: it meant a client could send `{"title": null}` explicitly, and the API would accept it with a 200 and silently set the task's title to null. The `status` and `priority` fields had the same gap, with no validator protecting them from null at all. I didn't catch this myself, and the AI-generated tests didn't catch it either, since the tests Claude suggested for those fields checked blank strings and missing fields, but never checked an explicit `null` on an existing field. The bug only surfaced when the facilitator reviewed the submission and pointed it out directly. That was a real lesson: AI-generated validation code and AI-generated tests can both look thorough while sharing the same blind spot, since they came from the same reasoning pass, so a second, independent form of review, in this case a human facilitator, still mattered.

Fixing it also changed how I thought about the design: I had to explicitly distinguish "the field was omitted" (leave unchanged) from "the field was sent as null" (should be rejected for title, status, priority, and tags, but is legitimately valid for description, assignee, and due_date). That distinction wasn't part of my original mental model of the feature, and only became clear once the failure was pointed out and I had to trace through why the existing tests hadn't caught it.
